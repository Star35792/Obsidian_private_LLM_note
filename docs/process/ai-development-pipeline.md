# AI 开发流水线

本文是 Note_Edit 项目的 AI 开发流程。默认入口是 [docs/README.md](../README.md)；本页只负责定义流程，不替代入口、当前计划或专题文档。它把一次需求从阅读上下文推进到代码、验证、记忆和 Git 提交，作为项目内可复用的工作协议。

## 总原则

- 用户当前指令优先于项目文档；项目文档之间以 `CONTEXT.md`、ADR、专题文档、动态状态的顺序解释冲突。
- 先读再改：先读取相关文档、代码和测试，再决定修改范围。
- 一次只推进一个可验证的主要目标，避免把尚未确认的需求直接扩展成大重构。
- 本地、可逆的编辑和测试可以直接执行；删除、覆盖未提交工作、推送和影响共享系统的操作必须重新确认。
- 输出先给结果和阻塞点，不给时间预估，不展示隐藏思维链。
- 每次任务开始先读取 [当前计划](../work/当前计划.md)，结束时更新计划和 [开发记录](../work/开发记录.md)。
- 每个动作按 [权限与确认规范](权限与确认规范.md) 判断是否可以继续；不确定就暂停，不靠猜测越过边界。

## 任务运行协议

把一次开发任务视为一个有状态的运行，而不是一段没有结构的聊天。状态只能按以下方向移动：

```text
todo -> in_progress -> verifying -> done
                    └-> blocked
```

- `todo`：已登记但未开始；`in_progress`：正在澄清或开发；`verifying`：代码已改完，正在跑验证；`blocked`：需要用户决定或外部状态变化；`done`：验收、记录和提交门槛全部满足。
- 不允许从 `todo` 直接跳到 `done`，也不允许用“代码写完”代替 `verifying`。
- 同一时间只保留一个主任务卡；需要并行时建立带父任务 ID 的子卡。
- 每次状态变化都要在当前计划中更新，关键节点追加开发记录。

### 任务卡最小字段

```markdown
## TASK-YYYYMMDD-NN：简短目标

- 状态：`todo`
- 目标：用户可观察到的行为变化
- 范围内：本次允许修改的模块/文档
- 范围外：明确不做的内容
- 验收：可执行的测试或手动场景
- 假设：不会改变路径的临时假设
- 风险：权限、数据、兼容性或回滚风险
- 依赖：前置任务、用户决定或外部服务
- 计划：1-5 个可单独验证的步骤
- 完成清单：每步完成后立即勾选
```

### 四个强制检查点

1. **Start Gate**：任务卡存在，需求边界和权限已判断。
2. **Plan Gate**：目标文件、测试策略、验收场景和不做项已写出。
3. **Verify Gate**：实现完成后运行相关测试、build、lint，并处理失败根因。
4. **Close Gate**：更新完成清单、开发记录、必要 memory，检查 diff 并提交或明确未提交原因。

任一检查点缺失，任务不能标记为 `done`。

### AI 每轮输出契约

每个自然阶段只报告四项，避免长篇过程污染工作上下文：

```text
状态：todo | in_progress | verifying | blocked | done
已完成：本轮已经产生的事实或文件
下一步：下一个可验证动作
阻塞/需要确认：没有则写“无”
```

工具调用前只说明动作目的；工具调用后只记录结果、影响和是否改变计划。不要把内部推理过程写入开发记录或 memory。

## 阶段与产物

### 1. 阅读上下文

目标是建立当前任务的事实边界，而不是立即提出方案。

阅读顺序：

1. [docs/README.md](../README.md)：确定本次任务进入哪一条树枝。
2. `CONTEXT.md`：术语、核心不变量和避免使用的旧称。
3. `docs/adr/`：已经做出的架构决策及其取舍。
4. `work/当前计划.md`、相关专题文档和 `memory/MEMORY.md`：当前状态、稳定约束和用户协作偏好。
5. 相关源码、测试、配置和 `git status`：确认文档与代码是否一致。

产物是简短的事实清单：当前实现、目标行为、明确限制、冲突点和待确认事项。

### 2. 需求澄清

把用户请求转换为可验收的需求，不把猜测写成事实。

必须明确：

- 用户要改变的行为，以及明确不改变的行为；
- 输入范围、输出形式、权限和确认边界；
- 验收场景和失败时的预期；
- 影响多个方案的未决选择。

如果缺少的信息不会改变实现路径，记录合理假设并继续；如果会改变范围、数据安全或架构，先向用户提问。澄清结果需要回写到任务记录或 ADR，而不是只留在对话中。

需求澄清结束时，必须把任务卡从“请求原文”收敛成“可验收行为”。如果仍有多个互斥方向，状态保持 `blocked`，不要同时实现多个版本。

### 3. 方案与切片

先找到现有相似实现，选择与当前架构一致的最小切片。方案应列出：

- 要修改的模块及其接口边界；
- 不需要修改的模块；
- 测试策略和端到端验收路径；
- 是否需要新增术语、ADR、配置或文件。

只有出现真实的不可逆取舍、未来读者难以理解且存在替代方案时才新增 ADR。不要为了“以后可能需要”创建抽象或文件。

### 4. 代码开发

- 修改前必须读取目标文件和调用方；修改已有文件优先于新建文件。
- 先写能表达需求的测试，再实现最小行为；修复发现的类型、安全和边界问题。
- 系统边界校验用户输入、外部 API、Vault 路径和模型输出；内部不可能发生的场景不添加无意义兜底。
- 保持 Note_Edit 的核心不变量：模型只能发起写工具调用，写入必须经过 `ChangePlan` 和用户确认。
- 变更保持局部，不顺手重构无关代码，不添加未经请求的兼容层。

### 5. 测试与验证

按风险选择验证范围，至少执行与改动相关的：

1. 单元测试：纯逻辑、解析器、边界和错误路径。
2. 集成测试：模块之间的接口、模型协议和 Vault Adapter。
3. 构建与 lint：`npm.cmd run build`、`npm.cmd run lint`。
4. 端到端或手动验收：按需求中的用户场景检查 UI、确认边界和实际写回。

失败时记录根因并调整方法，不重复无变化地重试同一命令。测试通过后检查 `git diff --check` 和工作区状态。

验证失败时，任务保持 `verifying` 或转为 `blocked`，不能提前写入 `done`。如果失败只影响本次切片，修复后重新跑最小相关验证；如果暴露了范围变化，回到 Plan Gate 更新任务卡。

### 6. 更新项目 memory

只把跨会话仍然有价值的内容写入 `docs/memory/`，并在 `work/开发记录.md` 记录本次变化：

- 已验证的架构约束和实现模式；
- 用户稳定的协作偏好；
- 当前阶段的完成项、已知限制和下一步；
- 容易重复犯错的边界规则。

不要写临时聊天上下文、未经验证的推测、重复的 `CONTEXT.md` 内容或完整测试日志。新增主题文件后，必须在 `docs/memory/MEMORY.md` 添加索引；更新时保持已有标题和 frontmatter 结构。

### 7. Git 提交

提交前并行检查 `git status`、`git diff`、`git log`，确认：

- 变更文件属于本次任务，没有把用户未授权的无关文件带入提交；
- 没有 API key、凭据或生成物；
- 测试、构建和 lint 状态已记录；
- 提交信息使用 Conventional Commits，说明行为变化和目的。

然后只暂存明确属于本次任务的文件，创建新的提交，不修改 Git 配置、不跳过 hooks、不 amend 已有提交。提交后再次运行 `git status`，把提交哈希和验证结果反馈给用户。

提交包至少包含：变更摘要、验证命令与结果、未提交文件说明、提交哈希。没有提交授权时，仍然完成 Close Gate，但明确标记“代码已验证，尚未提交”。

## 完成门槛

一次 AI 开发任务只有同时满足以下条件才算完成：

- 需求边界和验收标准已明确；
- 代码与测试已实现，相关验证通过；
- 稳定决策和跨会话经验已写入仓库文档或 memory；
- Git 提交只包含授权范围内的变更，工作区状态已说明。

## 会话记录模板

```text
目标：
已读取：
已确认：
未决问题/假设：
实现切片：
验证命令与结果：
写入 memory：
提交：
```
